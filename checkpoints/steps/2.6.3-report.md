## D. Risques et dépendances

- **Stock** : `size`/`color` utilisés dans l'affichage/tri des mouvements de stock — une suppression prématurée casserait ces écrans, pas la logique de calcul de stock (`syncProductStock()` n'en dépend pas).
- **Produits/variantes** : `products.taille` est `NOT NULL` — toute suppression future devra d'abord traiter cette contrainte (défaut `'N/A'` déjà en place).
- **`version`** : risque de confusion déjà désamorcé par un audit antérieur documenté dans le code ; les deux colonnes homonymes doivent rester traitées séparément.
- **Couverture générique** : `AttributeDefinition`/`ProductAttributeValue`/`ProductVariantAttributeValue` couvrent déjà les six codes candidats (`season`, `taille`, `equipe`, `size`, `color`, `version`-variante) via `AttributeDefinitionSeeder.php` — aucune lacune identifiée.
- **Activités** : aucune des cinq activités (Sport, VTC, Bébé, Moto, Artisanats du Maroc) n'a de statut privilégié dans le code actuel (`Product.php:265-281`) — cette neutralité est une garantie déjà en place, pas une décision de cette étape.

## E. Préconditions avant toute suppression future

1. Confirmation à 100 % que le catalogue existant a un enregistrement `ProductAttributeValue`/`ProductVariantAttributeValue` correspondant (rôle de `AttributeCrossCheckTest`/`BackfillAttributeValues`, déjà couverts par 2.6.2).
2. Migration de chaque point de lecture listé en section C vers le système générique, un fichier à la fois, avec tests dédiés.
3. Fenêtre d'observation en production avec double-lecture (colonne dédiée + attribut générique) avant toute `dropColumn`.
4. Backup DB vérifiable pris immédiatement avant toute migration destructive, jamais avant.
5. Décision explicite et séparée sur `products.version` (candidate à la suppression pure, usage nul confirmé) vs `product_variants.version` (activement utilisée, nécessite migration complète d'abord).

## F. Mécanisme de sauvegarde/restauration

Le système de checkpoint dispose déjà de `checkpoint.ps1 db -DbAction backup|verify|restore` (`checkpoints/lib/Commit.ps1`), testé de bout en bout (cycle backup → verify → corruption → verify → restore → verify) dans `checkpoints/tests/Run-SystemTests.ps1`. Réutilisable tel quel pour toute étape future nécessitant `requires_db_backup:true` — aucun nouveau développement requis pour cette précondition.
